# 第一阶段：可信基线实施记录与后续方案

**实施日期：** 2026-07-22  
**当前定位：** 单机开发与内部验证版  
**阶段目标：** 让项目具备可安装、可验证、可迁移的工程基线，并完成一次最小 GPU 训练闭环。

## 一、已完成的修改

### 1. 环境与依赖

- Python 基线统一为 3.12.13（`.python-version`）。
- 增加精确约束的直接依赖：PyTorch 2.11.0、torchvision 0.26.0、Ultralytics 8.4.102、Gradio 5.49.1、FastAPI 0.139.2、Optuna 4.9.0 等。
- 增加 `requirements-dev.txt`、`constraints.txt` 和 Windows/CUDA 12.8 环境快照 [requirements-lock-windows-cu128.txt](../requirements-lock-windows-cu128.txt)。
- 增加 Windows 安装脚本 [scripts/bootstrap.ps1](../scripts/bootstrap.ps1)：支持 `cpu` 和 `cu128` 两种 Torch wheel。
- 增加统一验证脚本 [scripts/verify.ps1](../scripts/verify.ps1)：执行依赖检查、编译检查、Ruff 和 pytest。
- 增加 `pytest.ini`、`pyproject.toml` 和 GitHub Actions CPU 测试工作流。

### 2. 配置路径可移植性

- [src/config_generator.py](../src/config_generator.py) 生成的 `data.yaml` 不再绑定旧电脑的绝对盘符，训练/验证/测试路径相对于 YAML 文件定位。
- 持久化训练配置中的项目内路径改为 POSIX 风格相对路径；运行时对象仍使用绝对路径，避免从非项目工作目录启动时解析失败。
- [src/data_validator.py](../src/data_validator.py) 改为读取数据集根目录下的 `data.yaml`，修复原来错误读取父目录的问题。
- 清理 `configs/**/*.yaml` 与 `dataset/*/data.yaml` 中的旧 `C:/`、`E:/` 路径；当前扫描结果为 0 个旧盘符引用，24 个 train/val/test 路径均可解析。
- 新增 3 个路径/类别一致性回归测试。

### 3. 受限环境运行稳定性

- [src/gradio_app/services/log_service.py](../src/gradio_app/services/log_service.py) 增加缺失的模块级 `logger`，修复 Ruff 报告的未定义名称。
- [src/__init__.py](../src/__init__.py) 将 Ultralytics、Matplotlib 的缓存目录指向项目 `.ci/`，默认使用 `Agg` 后端，避免依赖用户目录写权限和桌面环境。
- `.gitignore`、`.gitattributes` 和 [README.md](../README.md) 已补齐；训练产物、模型权重、数据图片/标签、缓存和日志不会进入版本库。
- Git 仓库已初始化，但按当前要求**不执行暂存或提交**；所有修改仍保留在工作区，等待人工审阅。

### GPU 烟雾训练

使用 `_smoke_test`、`yolov8n.pt`、160px、batch=2、1 epoch 完成：

```powershell
$env:POLARS_SKIP_CPU_CHECK = "1"  # 仅当前受限运行器需要
python train.py _smoke_test --model yolov8n.pt --imgsz 160 --batch 2 --epochs 1 `
  --override device=0 workers=0 cache=False
```

结果：

- 数据验证：通过（仅有小数据集规模警告）。
- 配置生成：通过，生成路径可随项目迁移。
- GPU 训练：通过，约 15.34 秒。
- 模型评估：通过，约 1.29 秒。
- 流水线总状态：成功，约 16.7 秒。
- mAP50/mAP50-95：0.0000；这是 2 张烟雾验证图的预期结果，不能作为模型质量指标。

第一次烟雾训练曾因 Polars 在当前沙箱识别不到 `sse3` 而失败；使用 Polars 自带的 `POLARS_SKIP_CPU_CHECK=1` 后训练闭环成功。真实部署时应确认机器 CPU 与 Polars wheel 兼容，不应盲目跳过 CPU 检查。

## 三、当前仍未解决的问题

1. `dataset/data` 缺失 75 个验证标签，不能用于正式基线。
2. 尚未完成一个真实数据集的正式训练、指标记录和模型质量评审。
3. Gradio 训练服务仍在线程内运行，并修改进程级 stdout/stderr；不支持可靠的多任务并发和进程重启恢复。
4. 训练完成后的产物、报告、配置和模型注册表尚未形成完整版本关联。
5. 当前锁文件是 Windows + CUDA 12.8 平台快照；CPU/Linux 仍由直接约束解析，后续应分别生成平台锁文件。

## 四、后续开发方案

### Phase 2：真实数据黄金路径（下一步，3–5 天）

优先使用已通过校验的 `cabel-damage-mini`，完成一次可复现正式基线：

- 先做 1–5 epoch 快速验证，再做正式训练。
- 固化数据集统计、类别分布、随机种子、配置、环境版本和模型哈希。
- 完成训练 → 评估 → `best.pt` → ONNX 导出 → FastAPI 推理闭环。
- 保存 `results.csv`、评估 JSON、混淆矩阵、预测样例和最终指标。

验收标准：任何开发者按 README 运行都能得到同一套完整制品和可解释的 mAP 指标。

### Phase 3：训练任务与制品管理（约 1 周）

- 将训练从 Web 线程迁移到独立子进程或任务队列。
- 增加任务状态持久化、可靠停止、失败重试和断点恢复。
- 接通 `ModelRegistry`，让数据集版本、训练配置、运行目录、报告和模型版本互相关联。
- 修复训练成功后清理过度的问题：保留报告和指标，采用可配置的归档策略。

### Phase 4：模型质量与实验管理（约 1 周）

- 将 Optuna 调参接入前端或统一 CLI 工作流。
- 增加历史实验对比、类别级指标、阈值调优和数据泄漏检查。
- 对完整数据集建立第一版质量门槛，例如 mAP、召回率、误报率和推理延迟。

### Phase 5：生产化（约 1 周）

- 提供 GPU Docker/部署说明、CI 中的 CPU 测试和发布制品。
- 远程服务强制 API Key、TLS、限流、上传大小限制和密钥管理。
- 增加磁盘配额、日志轮转、GPU/任务监控和失败告警。
